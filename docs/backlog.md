# 待解决问题与修复任务

本清单覆盖 sdn-controller、sdn-agent 和 sdn-web。优先级 P1 表示影响正确性或故障恢复，P2 表示影响长期运行、规模或运维，P3 表示后续能力扩展。状态以实际代码和验证结果为准。

## 持久化现状

两个服务已经有持久化，不能记为“完全没有持久化”：

- Controller：etcd 原子 CAS 快照；开发模式为文件 fsync + rename。保存节点、期望配置、任务、已应用基线和幂等收据。
- Agent：Redis 中保存 Candidate、Running、Operational、任务、Undo 和幂等收据；实验启用 AOF always。未设置 Redis 时使用文件日志。节点身份另存本地状态目录。
- 进程重启恢复日志与宿主机重启恢复实际网络是不同的能力。后者尚不完整：Linux 网络命名空间或主机重建后，不能仅凭旧 Running revision 认定接口、VRF、VXLAN 仍存在。
- 数据库必须配置持久化磁盘/卷；Redis 的落盘策略、备份和恢复演练仍属于部署要求。不能把 Redis 内存中的数据等同于已可靠落盘。

## REL-004：数据恢复后的配置自动重建

**状态：未实现；优先级：P1；所属：Agent、Controller。**

Agent 已实现身份、Redis/File 配置记录与任务日志的持久化恢复，以及未完成事务的补偿恢复。尚未实现的是：数据恢复后，核对 Linux/FRR 实际状态，并自动重新下发缺失或不一致的有效配置。

- 当前行为：已成功提交的 Running 操作记录和 revision 恢复后，不会自动重新执行；`ACCEPTED` 任务通过版本检查后执行，`APPLYING` / `ROLLING_BACK` 任务依据 Undo 补偿，`ROLLBACK_FAILED` 保留节点配置屏障。
- 影响场景：宿主机重启、容器网络命名空间重建，或 Linux/FRR 配置丢失后，即使原身份、Running 和成功任务仍在，bridge、VRF、VXLAN、地址、绑定及路由协议配置也可能缺失。不能仅凭旧 revision 或节点 RUNNING 状态判定业务网络已经恢复。
- 恢复边界：仅重启 Agent 且后端仍运行时，已有配置通常保留；FRR 自身启动加载已保存的 `frr.conf`，不代表 Agent 已实现自动重新下发。动态 MAC、ARP/ND 和协议会话需要重新学习或收敛。
- 待实现流程：建立当前有效配置模型 → 检测后端重建或配置丢失 → 查询实际状态 → 计算差异 → 按依赖顺序幂等下发 → 回读验证。Running 当前是成功操作日志，需考虑后续修改和删除，不能简单重放全部历史操作；恢复应限定受管资源，并与提交、回滚互斥。
- 验收要求：覆盖 Agent 进程重启、容器/网络命名空间重建、宿主机重启及后端配置丢失，分别验证持久化记录、实际 Linux/FRR 配置、重复恢复幂等性和业务连通性。
